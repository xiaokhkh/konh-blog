## 一句话结论

Karpathy 这次不是在给 "vibe coding" 做续集，而是在给它划边界：vibe coding 抬高了普通人做软件的下限，但专业软件开发真正进入的是 agentic engineering。LLM 不只是更快的补全器，而是一种新的计算环境；工程师的工作因此从记住 API 和手写局部实现，转向定义规格、组织上下文、协调 agent、验证输出、守住质量和安全边界。

## 1. December turning point：agentic workflow 开始真的可用

访谈开头，主持人引用 Karpathy 最近的说法：他作为程序员从未感到如此落后。这个说法有意思，因为它不是来自新手，而是来自长期站在 AI 工程前沿的人。

Karpathy 的解释是，过去一年他已经在用 Claude Code、Codex 这类 agentic coding 工具，但早期体验更像“帮你写一段代码，然后你还要修”。真正的变化出现在 2025 年 12 月左右：新模型生成的代码片段越来越少需要他改，他开始连续向系统要更多实现，并逐渐信任它完成更大块的工作。

这不是一个严格的基准测试结论，更像一线工程师的体感转折。但它提醒我们：如果一个团队对 AI 编程的印象还停留在早期 ChatGPT 代码片段阶段，判断可能已经过期。现在要重新评估的是完整 agentic workflow：读仓库、改文件、跑测试、调试、迭代、部署。

## 2. Software 3.0：prompt 和 context 变成程序

Karpathy 继续沿用自己的三阶段框架：

- Software 1.0：人写显式代码，计算机按规则执行。
- Software 2.0：人组织数据、目标函数和神经网络结构，模型权重成为程序。
- Software 3.0：LLM 成为可编程计算机，prompt 和 context window 成为程序，模型像解释器一样执行信息处理。

这个框架的关键不是“自然语言也能写代码”，而是“上下文就是控制面”。你给 agent 的 repo、文档、截图、错误日志、任务描述、约束和测试，都会改变它实际执行的程序。

他举了 OpenCode 安装方式的例子。传统思路会写一个复杂 shell script，以适配不同平台和环境；Software 3.0 的思路则是给 agent 一段说明，让它观察当前机器、做判断、执行安装、遇错调试。这里的“程序”不再是穷尽所有分支的脚本，而是一段能调动模型能力的上下文。

## 3. Menugen：有些 app 不是变快，而是会消失

访谈中最具体的例子是 Menugen。Karpathy 曾做过一个应用：用户拍餐厅菜单，系统 OCR 出菜名，再用图像生成模型给每道菜生成图片，最后把结果展示出来。按传统产品思路，这需要上传、OCR、生成、UI、部署、账号和一堆中间层。

后来他看到 Software 3.0 版本：直接把菜单照片给 Gemini，让图像模型把菜品图叠回原照片。输出就是一张增强后的菜单图。

这个例子的重要性在于，它不是“同一个 app 用 AI 写得更快”，而是“这个 app 的中间层可能不该存在”。当多模态模型可以直接从图片到图片、从原始上下文到目标结果，很多 OCR 加数据库加 UI 的胶水应用会被压缩成一次模型调用。

这对产品判断很残酷：不要只问 AI 能不能让现有流程提速，还要问这个流程是否应该被整个跳过。

## 4. Verifiability：AI 会先吃掉可验证领域

Karpathy 用可验证性解释 LLM 能力为什么进步不均匀。传统计算机擅长自动化“你能用代码精确定义”的东西；这一代 LLM 更容易自动化“你能验证输出对错”的东西。

数学、代码、测试、安全漏洞、游戏、形式化任务，都更容易构造强化学习环境。模型生成答案，系统自动验证，奖励信号清晰，能力就会快速堆上去。

反过来，写作、审美、组织判断、长期产品取舍也能部分验证，但成本更高、信号更软、反馈更慢。模型在这些地方就更容易表现出“看起来懂，但细节不可靠”的状态。

这也解释了为什么创业机会不只是“找 AI 还不会的领域”。更准确的问题是：这个领域是否能构造高质量验证环境？如果能，即使大模型实验室暂时没重点训练，团队也可能通过私有数据、环境和 fine-tuning 形成能力。

## 5. Jagged intelligence：能重构代码，也会犯简单错

Karpathy 反复强调 LLM 是 jagged intelligence：能力不是平滑分布，而是高峰和低谷并存。一个模型可能能重构十万行代码、发现漏洞，却在简单常识问题上给出荒唐建议。

这不是小瑕疵，而是使用方式的根约束。我们不能因为模型在某个可验证电路里表现惊人，就默认它在邻近任务里同样可靠。它的能力来自预训练数据、RL 环境和实验室选择的混合分布；如果你的任务落在这些“电路”里，速度会很快；如果不在，就会变得费力、脆弱、需要额外校准。

因此专业使用 LLM 的姿态不是“信任聪明助手”，而是“构造环境，让它在可检验边界内发挥”。测试、lint、模拟用户、红队攻击、schema、类型系统、审计日志，都会变得更重要。

## 6. Vibe coding vs agentic engineering

这是整场访谈的中心区分。

Vibe coding 的价值是 raising the floor：让更多人能做软件，让想法更快变成原型。它降低门槛，适合探索、侧项目、一次性工具、早期试错。

Agentic engineering 的价值是 raising the ceiling：让专业工程师用 agent 加速，但不牺牲生产软件的质量线。Karpathy 的态度很明确：不能因为代码是 vibe 出来的，就允许漏洞、不可维护性和错误身份模型进入生产系统。责任仍在工程师身上。

这也是为什么他把它叫 engineering。工程师要协调一组强大但随机、能力不均、会犯奇怪错误的 agent，让它们在约束下交付可验证结果。

## 7. 人类仍负责 spec、taste、design 和 oversight

Karpathy 举了 Menugen 的支付 bug：用户用 Google 账号登录，用 Stripe 购买 credits。agent 写代码时试图用 email 关联两边身份，但 Google email 和 Stripe email 可以不同。正确设计应该使用持久 user id，而不是把 email 当主键。

这类错误很典型。模型可能很会补 API、写 UI、接 Stripe、跑部署，但它不一定会自动守住系统身份模型。人类工程师不能只看“页面能跑”，还要检查数据模型、权限边界、业务不变量和失败路径。

因此工程师的价值没有消失，只是位置上移：

- API 拼写、样板代码、局部实现细节可以交给 agent。
- 架构、规格、约束、测试、审美、安全、数据一致性仍要人负责。
- prompt、docs、fixtures、tests、checklist 本身会成为一等工程资产。

## 8. Ghosts, not animals：不要把 LLM 当有动机的生物

访谈后段提到 Karpathy 的一个隐喻：我们不是在训练动物，而是在召唤 ghosts。意思不是玄学，而是提醒不要过度拟人化。

动物有进化来的动机、好奇心、游戏、恐惧、自保和稳定偏好。LLM 更像由预训练统计和 RL 奖励塑形出的模拟电路。你鼓励它、责备它、哄它，有时看似有用，但那不是在改变一个生物的内在动机，而是在改变上下文和采样路径。

这个心智模型的工程含义是：少做心理剧，多做环境设计。给清楚规格、真实文件、可运行测试、明确失败信号、可审计工具调用，而不是假设模型“理解了就会自觉负责”。

## 9. Agent-native 基础设施会成为新机会

Karpathy 对现在很多基础设施不满：文档、控制台、部署流程、配置页面仍然默认面向人。可是 agent 时代里，理想接口应该直接告诉 agent 怎么做，给它结构化数据、权限、传感器和执行器。

他希望未来能直接说“构建并部署 Menugen”，agent 自动创建项目、配置服务、接入域名、设置 Vercel 和依赖，而不是让人一层层点控制台。

这背后是一个清晰机会：谁能把自己的产品、云服务、SDK、文档和控制面做成 agent-native，谁就会在 Software 3.0 里更容易被调用、集成和自动化。

## 10. 教育：思考可以外包，理解不能外包

结尾最有价值的一句话是：you can outsource thinking, but you can't outsource understanding。

Karpathy 的解释很实际。即使模型能生成大量方案、代码和分析，信息仍然要进入人的脑子。人仍要知道要做什么、为什么值得做、如何指导 agent、结果是否合理。

这不是“人类永远不可替代”的安慰，而是一个更硬的约束：如果你没有理解，就无法提出好规格，无法识别 agent 的怪错，也无法判断一个系统是不是在解决真问题。

未来的学习重点不是背更多 API，而是建立能指导 agent 的理解力：系统边界、数据模型、验证方法、产品判断、审美标准、失败模式和长期维护成本。

## 对我们自己的 workflow 的启发

这条视频对实际工程流程有几个直接启发：

1. 把任务写成 spec，而不是只写一句需求。agent 越强，规格的价值越高。
2. 把测试、lint、类型、CI、模拟用户和红队攻击前置，尽量把任务放进可验证环境。
3. 不要只让 agent 写代码，也要让多个 agent 审查、攻击、解释和压缩上下文。
4. 对新产品先做 Software 3.0 消亡测试：这个 app 会不会被一次多模态模型调用替代？
5. 评估 AI-native 工程师时，看大项目组织能力、验证能力和工具利用能力，而不是只看手写小题。
6. 保持 production bar。vibe coding 可以用于探索，但上线仍要工程纪律。

## 最后判断

这场访谈的核心不是“Karpathy 又造了一个新词”，而是他在把 AI 编程从兴奋期拉回工程期。

Vibe coding 证明了普通人可以更快接近软件；agentic engineering 要回答的是专业团队如何在 agent 时代继续交付可靠软件。前者让世界产生更多原型，后者决定哪些原型能变成生产系统。
