## 一个常见的反差

在不少生产代码库里，你会看到这样一种反差：同一个功能模块，甚至出自同一个团队、同一段时间，却写出了两份命运完全不同的代码。

一份是动辄数千行的“上帝服务”：一个类，塞进几十个依赖。AI 改它，基本靠赌：要么读不全，要么读全了也被淹没在中间。

另一份是同一目录下的小文件集合：用一个结构化的状态对象把整条流水线的数据形状钉死，再用一张流程图把步骤拆成 `准备上下文 -> 执行 -> 收尾` 几个节点，每个节点是一个能单独读懂、单独改、单独测的小函数。AI 改它，稳。

差别往往不在工程师的水平，是同一拨人。差别在于：**第二份代码装得进 AI 的工作记忆，第一份装不进。** 这就是 AI 友好工程要解释的全部现象，也是它的第一性原理。

## 第一性原理：注意力是有限且会衰减的

Karpathy 有个被反复引用的类比：LLM 像一种新的操作系统，模型是 CPU，**上下文窗口就是 RAM**，是它的工作记忆。

但 RAM 这个比喻还不够狠。真正的约束有两层：

第一，**有效上下文远小于技术上下文**。模型标称能吃几十万 token，不代表它在那么长的上下文上还聪明。信息在开头和结尾被可靠记住，塞在中间的会 “lost in the middle”。

第二，**注意力是会被稀释的预算**。每多一个 token，平均都在削弱之前 token 的影响力，尤其当新内容和旧内容语义重叠时。

把这两层合起来，第一性原理就一句话：

> AI 友好工程，是为“有限且会随长度衰减的注意力”而设计代码，而不是为人类的阅读审美，也不是为机器的执行效率。

人类时代的很多直觉，是为“无限耐心 + 跨文件长期记忆”的读者优化的。AI 没有这两样。下面每一条实践，都是从这条原理里推导出来的，不是拍脑袋的风格偏好。

## 推论一：小，才装得进

一个几十行的小模块，AI 要改它，一次性把整条链路读进工作记忆还绰绰有余。

而一个数千行的巨型文件则触发双重惩罚：一是单次读不进有效窗口；二是就算硬塞进去，中间那几千行正好落在 “lost in the middle” 的盲区。**它的难改程度，比行数显示的还要糟。**

所以“单文件控制在数百行、单类依赖控制在个位数”不是洁癖，是把代码单元压到注意力能完整覆盖的尺寸。这件事值得做成 CI 门禁，而不是口头约定：存量挂白名单，新增超标直接 fail。

## 推论二：一致，才导航得动

AI 找代码，不是靠预先嵌入整个仓库，而是靠 grep、读文件、看命名一步步探索。2026 年的明显转向，是从“到处 RAG”回到 “agentic search”。Anthropic 把这叫**渐进式披露**：文件大小暗示复杂度，命名暗示用途，目录结构暗示边界，agent 顺着这些信号一层层拼出理解。

推论很直接：**结构越可预测，agent 越少把注意力浪费在“东西在哪”，越多花在“问题本身”。**

具体做法，是给每类模块一套固定骨架，例如 `控制器 / 服务 / 仓储 / 契约` 四件套，让 AI 新增功能时能猜对该放哪。代价只有一个：别开一致性的口子。一旦某个模块偷懒省掉了某一层，把逻辑混进别处，AI 会忠实地复制这个坏样板。

## 推论三：显式，压倒隐式，连 DRY 都要让位

这一条反人类直觉，但有人专门写了论文论证：为人类可读性优化的传统约定，简洁、隐式模式、稀疏注释，和 agent 的能力是**根本错配**的。

它给的几条，刀刀见血：

- **全名压倒缩写**：模糊的简写要靠领域知识才能解码，而 agent 不一定有那份知识。
- **意图写进代码**：agent 不像人那样跨文件记住上下文，所以把“为什么”内联进来，而不是丢在外部文档里。
- **战略性重复 > 聪明的抽象**：DRY 不是圣经。对 agent 来说，把不同代码路径显式写开，比一个需要复杂抽象推理才能拆解的“优雅”复用更好懂。

核心转变是：**从“最小化行数 / token”，转向“最大化每 token 的可理解度”。** Token 便宜，注意力贵。一段多花 20 token 但让 agent 一次读懂的显式代码，比省下 20 token 却要它来回推理的精巧代码，划算得多。

## 推论四：状态机，压倒上帝类

推论一和推论三在这里合流。一个对 AI 友好的流程编排，通常长这样：

```python
# 契约即状态：整条流水线的数据形状被一个结构体钉死
class TurnWorkflowState(TypedDict):
    user_id: NotRequired[str]
    context: NotRequired[TurnContext]
    perf_stages: NotRequired[dict]   # 连性能埋点都在契约里

# 流程即图：每个节点是输入输出都为 state 的小函数
graph.add_node("prepare_context", self._prepare_context)
graph.add_node("run_turn", self._run_turn)
graph.add_node("complete_turn", self._complete_turn)
```

这正中一条被反复验证的原理：**把结构化状态独立于消息流维护。** 没有结构化状态，关键信息会随着对话滑出窗口而丢失；有了它，关键事实独立持久，每次调用都能注入。

那个状态结构体就是 agent 的外置工作记忆；每个节点是一个能独立装载、独立验证的小单元。改某一个节点，只需读这个节点加状态定义，**不用扛着几千行**。

反过来，一个注入了几十个依赖的上帝类，恰恰要求 agent 在脑子里同时持有整条流水线。如果代码里出现一堆 `xxx_compat_mixin` 之类的命名，通常说明拆迁早就开始了，只是卡住了。**对这种半成品，优先收尾，而不是开新坑。**

## 推论五：活的护栏，压倒死的文档

最反直觉的一条：**错的文档不是中性的，是负资产。**

一个典型场景：团队换了技术栈，但约束 AI 行为的那条 lint 规则，glob 还指向旧框架的文件路径，而且没设成强制生效。这条护栏指向一组不存在的文件，它没在保护你，它在占着位置假装保护你。项目说明文件同样，常常过期到还在描述上一代架构。

研究给了数字：一项关于 AGENTS.md 的研究发现，**人工精修的上下文文件带来约 +4% 的成功率，而 LLM 自动生成的反而 -3%**，两者都附带 20% 以上的成本开销。结论是，内容质量比“有没有”重要得多。换句话说，一份错的规则，既花你的注意力预算，又把 agent 带偏，双重扣分。

所以“活护栏”有三个判据：

1. **可被 grep 验证**：能写成一条 `grep -r` 自检命令的规则，agent 才会真遵守；靠散文式的劝导，它会忽略。
2. **CI 强制**：测试是 agent 犯错时的安全网。别指望它“自然就对”。把“小文件、能力收口”做成门禁，而不是口号。
3. **对抗模式腐烂**：agent 引入新模式、旧模式没删干净，下一个 agent 就会照抄旧的。要主动重构，趁复杂度还没复利之前就把组件抽出来。

## 它到底改变了什么

AI 友好工程不是某种新框架，而是一次优化目标的反转。

人类时代，我们为“无限耐心、能跨文件记忆、讨厌重复”的读者写代码，于是推崇 DRY、简洁、自解释、“注释是坏味道”。AI 时代的读者恰恰相反：**注意力有限、不跨文件记忆、被冗长稀释。** 于是天平倒向小文件、显式命名、内联意图、可预测结构、活的护栏，哪怕多花些 token。

判断一段代码是不是 AI 友好，只需一个测试：

> 一个没有任何记忆的全新 agent，能不能只加载一个文件，就读懂它的契约、改对它、并验证它？

能，就是 AI 友好。如果它必须在脑子里同时扛着几千行代码和一肚子部门黑话，就不是。

剩下的工作，往往不是发明新东西，而是把团队内部已经跑通的“小而显式”的范式，推广到那几块还没拆完的巨石上，并且，先把那些指向幽灵文件的规则修活。
