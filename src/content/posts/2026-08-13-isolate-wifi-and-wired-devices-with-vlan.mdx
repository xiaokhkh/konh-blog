最近给一套已经在运行的局域网增加隔离网络。要求看起来很简单：原来的管理网不能动，指定 Wi-Fi 和后续接入的有线设备进入新网段，并且新旧网段不能互访，但都要能上网。

真正容易出错的地方，不是创建 VLAN 本身，而是让同一个 VLAN 标签完整穿过网关、每一级交换机和 AP。任何一跳没有放行，最常见的现象就是设备可以连上 Wi-Fi，却一直拿不到 DHCP 地址。

这篇是完整脱敏后的复盘。地址、VLAN ID、端口、SSID、MAC、序列号、场地、设备名称和厂商界面均已删除或替换。示例值仅用于说明，不能直接照搬到生产环境。

## 目标与示例参数

假设现有网络如下：

| 用途 | 示例配置 |
| --- | --- |
| 原管理网络 | `10.20.10.0/24` |
| 原网关 | `10.20.10.1` |
| 隔离网络 | `10.20.30.0/24` |
| 隔离网关 | `10.20.30.1` |
| 隔离 VLAN | `VLAN 30` |
| DHCP 地址池 | `10.20.30.100-10.20.30.199` |

VLAN ID 和 IP 地址的第三段不需要相同。这里都用了 `30`，只是为了减少运维时的认知负担。

## 先建立整体心智模型

这类配置里同时出现 VLAN、子网、DHCP、Trunk、Access、路由和 ACL，容易把它们误认为同一件事。实际上，它们分别解决不同层次的问题：

| 概念 | 所在层次 | 解决的问题 |
| --- | --- | --- |
| VLAN | 二层 | 哪些端口和终端属于同一个广播域 |
| Access / Trunk / Hybrid | 二层端口行为 | 无标签终端如何入网、多个 VLAN 如何共享一条链路 |
| IP 子网 | 三层 | 终端使用哪组地址，以及什么流量需要经过路由 |
| DHCP | 应用层服务 | 自动下发地址、掩码、网关和 DNS |
| 子接口 / SVI | 三层网关接口 | 让某个 VLAN 拥有默认网关并参与路由 |
| ACL / 防火墙 | 三层及以上 | 哪些源可以访问哪些目的和服务 |

可以用一句话记住：

> VLAN 决定报文在哪个二层空间里传播，网关决定不同空间之间如何转发，ACL 决定哪些转发被允许。

同一个 VLAN 通常映射到一个 IP 子网，但这是一种清晰、常见的设计约定，不是协议强制要求。不要用“VLAN 30 就一定是 `x.x.30.0/24`”反推未知网络。

最终链路可以抽象成：

```text
网关父接口（原网络 Untagged）
└── VLAN 30 子接口（隔离网络 Tagged）
        │
        ├── 交换机上联：Native/Untagged 原网络，Tagged VLAN 30
        ├── 中间交换机上联：Native/Untagged 原网络，Tagged VLAN 30
        └── AP 接入口：Native/Untagged 原网络，Tagged VLAN 30
                ├── AP 管理地址：原网络
                └── 隔离 SSID 客户端：VLAN 30
```

## 第一步：在网关创建 VLAN 子接口

在承载原管理网络的物理接口上创建逻辑子接口：

```text
父接口：LAN/MGMT
子接口 VLAN ID：30
子接口地址：10.20.30.1
掩码：255.255.255.0
```

父接口继续保留原来的 `10.20.10.1/24`，不要修改。子接口收到带 `VLAN 30` 标签的报文后，才会把它们送入 `10.20.30.0/24`。

有些设备会把子接口命名为类似 `GiX/Y.30`。末尾的 `.30` 通常是逻辑子接口编号，真正决定 802.1Q 标签的是配置里的 VLAN ID；两者往往一致，但排障时仍应查看实际字段，不要只凭接口名猜测。

## 第二步：给子接口配置 DHCP

为隔离网络建立独立 DHCP 地址池：

```text
网络：10.20.30.0
掩码：255.255.255.0
范围：10.20.30.100-10.20.30.199
默认网关：10.20.30.1
DNS：按组织策略填写
```

不要把网关地址放进可分配范围。部分网关会自动把 DHCP 池关联到子接口，部分型号需要手动选择接口，保存后要再次确认绑定对象。

`100-199` 只有 100 个地址，但不代表 `/24` 只能容纳 100 台设备。需要更多租约时，可以在避开网关、静态地址和保留区的前提下扩大地址池。不要用“动态 VLAN”解决单个地址池不足；动态 VLAN 主要用于按身份或策略把终端放进不同 VLAN。

## 第三步：SSID 只负责给客户端打标签

在 AP 或无线控制器中，把目标 SSID 的 VLAN 设置为 `30`。客户端发出的流量会由 AP 加上 `VLAN 30` 标签，再送到有线网络。

这里最容易混淆三件事：

- **AP 管理地址不用改。** AP 仍然从原网络获得管理 IP，才能继续被控制器发现和管理。
- **不要把 AP 的 WAN/管理 VLAN 改成 30。** 那是在改变 AP 自身的管理链路，配置不匹配时 AP 会直接离线。
- **AP 的有线 LAN 口 VLAN 不等于 SSID VLAN。** 前者通常控制插在 AP 下行网口的设备，后者控制无线客户端。

因此，一个典型 AP 端口同时承载两类流量：

```text
原管理网络：Untagged / Native
VLAN 30：Tagged
```

AP 管理 MAC 继续出现在原 VLAN 中是正常现象。真正需要检查的是无线客户端的 MAC 是否被学习在 VLAN 30。

### 一个无线报文到底怎么走

以手机连接隔离 SSID 并申请地址为例：

1. 手机通过 Wi-Fi 发出无 802.1Q 标签的 DHCP Discover。
2. AP 根据 SSID 配置，把它映射到 VLAN 30，并从有线口发出 Tagged 报文。
3. 每一级交换机读取 VLAN 标签，在允许 VLAN 30 的上联端口继续转发。
4. 网关的 VLAN 30 子接口收到广播，由对应 DHCP 服务返回 Offer。
5. 回程报文沿相同 VLAN 返回 AP；AP 去掉有线侧标签，通过无线发给手机。

所以“连上 Wi-Fi”只证明无线认证和关联成功，不代表 VLAN、交换链路或 DHCP 已经打通。

## 第四步：让 VLAN 穿过每一级交换机

如果网关和 AP 之间经过多台交换机，VLAN 30 必须在每一段上联链路中连续放行。一台交换机配置正确，不代表整条路径已经打通。

交换机之间、交换机到网关、交换机到 AP 的端口可以使用 Trunk，也可以使用等价的 Hybrid 配置：

```text
端口模式：Trunk 或 Hybrid
Native VLAN：原管理 VLAN
允许通过：原管理 VLAN、VLAN 30
原管理 VLAN：Untagged
VLAN 30：Tagged
```

如果设备界面只显示 `Permit VLAN`、`Untag VLAN`，等价目标是：允许原 VLAN 和 VLAN 30，通过时只去掉原 VLAN 的标签，保留 VLAN 30 的标签。

不要因为某个端口“已经属于 VLAN 30”就认为完成了。还要查看端口模式、Native VLAN，以及 VLAN 30 出口是否为 Tagged。

## 第五步：NAS 等普通有线终端使用 Access 口

普通 NAS、电脑或打印机通常不会主动发送 VLAN 标签。要让它进入隔离网络，应把它连接的交换机端口设置为：

```text
端口模式：Access
Access VLAN：30
```

交换机会给终端发来的无标签报文归入 VLAN 30，并在发往终端时去掉标签。NAS 本身使用 DHCP 即可获得 `10.20.30.x`；如果使用静态地址，则网关应填写 `10.20.30.1`。

只有在终端明确支持并已配置 802.1Q 时，才考虑给终端 Trunk。单网段 NAS 使用 Access 口更简单，也更不容易误配。

### 为什么终端不需要知道 VLAN ID

Access 端口就是交换机与普通终端之间的翻译边界：终端只收发普通以太网帧，交换机在内部为它归类。VLAN 标签主要存在于交换机、AP、虚拟化主机和网关之间的链路上。

这也是为什么把普通终端直接接到 Trunk 端口，往往会落入 Native VLAN，而不是期望的隔离 VLAN。

## 第六步：VLAN 不等于安全隔离

创建两个 VLAN 只完成了二层广播域分离。因为两个网段都直连在同一台网关上，网关会天然拥有它们的路由；如果没有 ACL、防火墙区域或安全策略，两个网段通常仍然可以互访。

需要双向隔离时，可以建立一组扩展 ACL，按顺序匹配：

```text
1. 禁止 10.20.30.0/24 → 10.20.10.0/24
2. 禁止 10.20.10.0/24 → 10.20.30.0/24
3. 允许其他必要流量
```

然后将 ACL 应用到隔离子接口的合适方向：

- `in`：处理从隔离网络进入网关的报文；
- `out`：处理网关准备发往隔离网络的报文。

不同厂商对“掩码”的输入含义不完全一致。有的页面要求 `255.255.255.0`，有的 ACL 命令使用通配符 `0.0.0.255`。应以界面示例和校验提示为准，不能混用。

最后一条“允许任意到任意”只适合 ACL 已经准确绑定到目标接口、前置拒绝规则完整的场景。网络里还有其他内部网段时，更稳妥的做法是显式允许上网、DNS、NTP 等必要流量，而不是长期保留过宽的兜底规则。

还有一个容易忽略的边界：阻止隔离网段访问原管理网，并不一定会阻止它访问网关在隔离网段上的本地地址。若不希望隔离终端打开路由器 Web、SSH 或 API，还要单独配置设备管理服务的来源限制，或禁止这些服务在隔离子接口监听。

### “双向禁止”与有状态防火墙

无状态 ACL 逐包判断，通常需要分别考虑两个方向；有状态防火墙会记录连接，能够允许已建立连接的返回流量。两者不能只凭页面名称互相替代。

例如，若希望管理网可以主动维护 NAS，但 NAS 不能主动访问管理网，最合适的是有状态策略：允许管理网发起连接并放行返回流量，同时拒绝隔离网主动发起。简单的双向禁止会把管理能力也一起切断。

## 拿不到 DHCP 地址时，按路径排查

设备能连接 SSID、却拿不到地址，通常表示无线关联成功，但 DHCP 广播没有完整到达网关。最短排查顺序是：

1. 确认 SSID 的 VLAN ID 与网关子接口一致。
2. 确认 AP 自身仍在线，管理地址仍属于原网络。
3. 确认 AP 接口允许 VLAN 30 Tagged。
4. 沿 AP 到网关的方向，逐台确认所有交换机上联允许 VLAN 30 Tagged。
5. 确认连接网关的交换机端口同样允许 VLAN 30。
6. 确认子接口处于连接状态，DHCP 池已启用并绑定正确。
7. 让客户端断开重连或更新 DHCP 租约，避免继续使用旧地址。

一个非常有效的二分测试，是找一个空闲交换机端口临时设置成 `Access VLAN 30`，插入笔记本：

- 笔记本能获得隔离地址：网关、DHCP 和交换机上联基本正常，问题集中在 AP 或 SSID 标签。
- 笔记本也无法获得地址：继续检查网关、DHCP 或上联链路，不要先折腾无线参数。

MAC 地址表也很有用：同一 MAC 在哪台交换机、哪个 VLAN、哪个端口被学习，可以还原真实链路。普通终端口往往只出现一两个 MAC；上联口通常会学习到大量下游 MAC。LLDP 邻居比凭端口号猜拓扑更可靠。

## 边缘知识：理解得更完整

### MAC 表和 ARP 表不是一回事

交换机的 MAC 地址表回答“这个二层地址从哪个端口可达”，记录的是 `VLAN + MAC → 端口`。网关和终端的 ARP 表回答“这个 IPv4 地址对应哪个 MAC”，记录的是 `IP → MAC`。

排障时，可以先用 DHCP 或 ARP 找到目标 IP 对应的 MAC，再用交换机 MAC 表逐级定位端口。看到同一个上联口学习到很多 MAC 是正常的；看到一个普通终端口不断出现多个陌生 MAC，才需要检查它后面是否还有交换机、虚拟化桥或错误接线。

### VLAN 隔离的是广播域，不是无线客户端彼此隔离

同一 SSID、同一 VLAN 中的客户端仍可能二层互访。如果访客或 IoT 设备之间也不能互相访问，还需要启用 AP 的客户端隔离、无线用户隔离或私有 VLAN 等功能。

### `/24`、DHCP 地址池和在线设备数

`/24` 提供 256 个地址，其中网络地址和广播地址不能分配，网关、静态地址、保留地址也会占用空间。DHCP 池只描述服务器当前愿意出租的那一段，并不改变子网本身的容量。

扩大地址池之前，应先检查租约时长和历史客户端数量。大量手机使用随机 MAC 时，同一物理设备也可能留下多个租约。真正超过一个 `/24` 的合理容量后，再考虑更大的子网或按用途拆分多个 VLAN，而不是简单堆叠多个重叠地址池。

### Native VLAN 为什么危险

Trunk 上的无标签流量会被归入 Native VLAN。链路两端 Native VLAN 不一致时，无标签报文可能进入错误网络，既会造成管理面失联，也可能形成安全边界缺口。

因此，上联两端要同时核对：允许 VLAN 列表、Native VLAN，以及各 VLAN 的 Tagged/Untagged 行为。只看一端或只看 VLAN 成员列表不够。

### Trunk 不会自动制造环路，但多余链路会

额外允许一个 VLAN 一般不会直接影响现有转发，但多接一根交换机链路可能形成二层环路。环路会引发广播风暴和 MAC 地址漂移。交换机之间若存在冗余物理链路，需要正确启用 STP/RSTP 或把链路做成受支持的聚合组，不能把两根线简单并接。

### VLAN 不是加密

802.1Q 标签用于逻辑分段，不提供机密性或身份认证。关键业务仍需要 TLS、设备认证、最小权限和补丁管理。VLAN 是缩小攻击面的一层，不是完整安全方案。

### IPv6 也要纳入隔离策略

只配置 IPv4 ACL，不代表 IPv6 已隔离。若网络开启 IPv6，终端可能通过 IPv6 邻居发现、路由通告和默认路由建立另一条通信路径。要么同步设计 IPv6 地址、RA/DHCPv6 和防火墙策略，要么明确关闭未使用的 IPv6 服务。

## 延伸阅读路线

如果希望从“会配置”继续走向“能设计和排障”，可以按下面顺序阅读：

1. **以太网与交换学习**：帧、MAC 地址、广播、未知单播、MAC 表老化。
2. **IEEE 802.1Q**：VLAN tag、VID、Tagged/Untagged、Native/PVID。
3. **IPv4 子网与默认网关**：子网掩码、最长前缀匹配、ARP、跨网段路由。
4. **DHCP DORA 流程**：Discover、Offer、Request、Ack，以及广播为何依赖二层路径。
5. **交换机端口模型**：Access、Trunk、Hybrid，以及不同厂商术语之间的映射。
6. **ACL 与有状态防火墙**：规则顺序、入方向/出方向、返回流量和默认策略。
7. **STP/RSTP 与链路聚合**：多交换机网络如何避免环路并提供冗余。
8. **无线到有线的 VLAN 映射**：SSID、AP 管理 VLAN、用户 VLAN、客户端隔离。

推荐优先阅读厂商配置指南和标准组织资料，并把配置前后的 MAC 表、ARP 表、DHCP 租约和路由表作为证据保存。网络排障最可靠的方式不是记住某个界面选项，而是逐跳回答：报文现在有没有标签、属于哪个 VLAN、从哪个端口进入、应该从哪里出去。

## 验收清单

配置完成后，至少验证下面几项：

- 隔离 SSID 客户端获得 `10.20.30.x`，网关为 `10.20.30.1`。
- 隔离客户端能访问互联网和必要的公共 DNS。
- 隔离客户端不能访问原管理网中的主机。
- 原管理网主机不能主动访问隔离终端（如果目标是双向隔离）。
- AP 和交换机仍使用原管理地址在线。
- 插在 Access VLAN 30 端口的 NAS 获得隔离地址。
- 原网络中的现有 SSID、有线设备和管理入口不受影响。
- 网关本地管理服务只对预期来源开放。

## 变更时最值得坚持的顺序

生产网络里，不要先批量修改所有 AP 和上联口。更安全的顺序是：

1. 备份网关与交换机配置，记录真实端口拓扑。
2. 创建网关子接口和 DHCP。
3. 从网关侧向 AP 侧逐跳放行 VLAN。
4. 用一个 Access 测试口验证 DHCP。
5. 新建临时 SSID 验证无线链路。
6. 确认稳定后再迁移正式 SSID 和有线终端。
7. 最后启用 ACL，并分别测试上网、双向隔离和设备管理面。

变更 Native VLAN、AP 管理 VLAN 或正在承载上联的端口，最容易造成整段网络失联。没有带外管理时，必须为每一步保留明确的回滚路径。

## 复盘结论

这次配置最重要的不是某个厂商页面应该勾哪一项，而是理解报文在整条路径上的形态：

```text
客户端无标签流量
→ AP 按 SSID 加 VLAN 标签
→ 所有上联保持标签并放行
→ 网关子接口解封装并提供 DHCP/路由
→ ACL 控制它能访问哪些网络
```

AP 管理网络可以保持不变，SSID 客户端仍然进入新的隔离网段；有线 NAS 则通过 Access VLAN 加入同一网段。只要标签在每一跳都连续、DHCP 绑定正确、路由边界有明确策略，就能在不扰动原网络的前提下完成隔离。
