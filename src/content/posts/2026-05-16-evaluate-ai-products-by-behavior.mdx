This essay is the English synthesis of the April 24 to May 6 staging chat, location-chat, and minigame test reports in the [Recent Lark Documents](/posts/2026-05-16-recent-lark-documents/) index.

The source documents are not only QA records. They show a useful evaluation style for AI products: capture behavior, context, transcript evidence, metrics, and the next regression target.

## Key takeaways

- AI product tests should preserve behavior and context, not just a pass/fail outcome.
- Transcript images, raw transcript, speed metrics, and issue lists each serve a different review purpose.
- Good test reports convert qualitative failures into reusable regression cases.

## Source alignment

The staging reports repeatedly track concrete dimensions:

- world channel behavior,
- single chat behavior,
- location chat behavior,
- location minigame entry,
- participant drift,
- fallback rate,
- first delta latency,
- turn completion latency,
- transcript quality,
- visible agent reply count.

The May 6 reports also show the value of visual evidence: summary board images and imagegen transcript cards were inserted at the top of the Lark docs, while raw text and metrics stayed below for audit.

## Record the failure shape

The most useful source reports describe failure shape, not only status.

Examples from the test notes include:

- start challenge was dragged by old normal-chat context,
- visible replies mixed in old history or replay fragments,
- wrap-up could fail because characters continued the old gameplay,
- suggestions improved from zero in one run to most turns in a later run,
- a `role='system'` write failure blocked a new-player challenge offer,
- world channel fallback disappeared in one retest but public discussion still needed follow-up.

These are better than "failed" because they tell the next engineer what to reproduce.

## Separate metrics from judgment

The reports keep both numbers and product judgment:

- first stream latency,
- turn done latency,
- number of real agent replies,
- fallback count,
- participant drift,
- whether the scene felt natural,
- whether the user could repair or wrap up the flow.

That combination matters. An AI turn can pass the API test and still feel wrong to the user.

## Convert reports into regression fixtures

Each meaningful issue should become a small fixture:

- setup state,
- user message,
- expected behavior,
- unacceptable behavior,
- observed failure,
- fixed behavior,
- source transcript or screenshot.

That is how subjective AI QA becomes an engineering loop.
