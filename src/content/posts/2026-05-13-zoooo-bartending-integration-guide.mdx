> 适用范围：`konh/bartending-zoooo-location-chat` / PR #596目标：把“地点群聊”里新增的调酒场景讲清楚，方便前后端、QA、产品一起联调。
## 1. 联调目标
本次链路不是把调酒做成一个独立聊天系统，而是在原有地点聊天认知和推荐回复链路上增加一个短生命周期的“调酒会话”。
核心目标：
- 玩家进入地点后，每次调酒都要有独立 `conversationId`，不能把调酒评分、配方、通过/不通过数据泄漏到普通地点群聊。
- 客人可以像地点群聊里的 agent 一样闲聊，但上下文只弱约束“正在点酒/描述口味/回应玩家提问”。
- 玩家完成调酒后，结算反馈由调酒链路展示；最后一条角色 chat 不直接消费“小费/评分”等技术结算信息。
- 推荐回复必须是“label 即可发送短句”，每次顾客回应后都要刷新，语气像玩家自然追问，不要出现口吻错乱。
- 不接受兜底人格内容。模型失败时表现为 retry / 错误提示，而不是生成奇怪 fallback 台词。

## 5. 会话隔离规则
### 5.1 地点进入周期
`locationVisitId` 表示“这次进入地点”的生命周期。agent 离开再回来要刷新；同一次停留中保持稳定。
规则：
- `locationVisitId = worldId + locationId + timestamp`
- 同一地点停留期间不随 React 重渲染变化。
- `agentLocationVisitId = locationVisitId + agentId`
- 预制需求只在这个 visit 范围内顺延，避免客人重复喝上一轮的酒。
### 5.2 调酒会话周期
每位客人进入调酒都创建新的 `sessionId` 和 `conversationId`。
规则：
- `sessionId` 管调酒状态：asking / completed / closed。
- `conversationId` 管这轮顾客对话历史。
- 普通地点群聊不读取调酒隐藏 marker。
- 调酒中间数据只出现在调酒 session 内，不出现在群聊地点上下文。
## 6. 数据字段
前端提交调酒结果时，`selection` 至少包含：
- `cupId`
- `baseIds`
- `baseId`
- `mixerIds`
- `garnishId`
- `tags`
后端评分时要同时兼容：
- 新结构：`baseIds: string[]`
- 兼容结构：`baseId: string | null`
联调重点：基酒不能丢。评分、推荐、展示都要读到同一份配方选择。
## 7. 推荐回复规则
推荐回复属于玩家可点击短句，不是系统解释。
要求：
- 每次顾客回应后刷新。
- label 本身就是可发送短句。
- 口吻像玩家自然追问。
- 不使用“老板”“调酒师身份说明”等额外设定。
- Day2 剧情引导模式下，推荐回复必须走固定引导，不被后端推荐覆盖。
示例方向：
- “那你想要更清爽一点？”
- “酸一点可以吗？”
- “你不想要太甜，对吧？”
- “要不要留一点辛辣感？”
## 8. 过 / 不过的预期表现
通过：
- 顾客 chat 保持角色口吻。
- UI 展示 `passed=true`、score、reviewText。
- 结算反馈可以提口味是否命中，但不要求角色 chat 说“小费/评分”。
- 可以进入下一位顾客。
不过：
- UI 展示 `passed=false`、score、reviewText。
- session 保持 `asking`，允许玩家重新调。
- 不要用 fallback 生成“很怪的顾客台词”。
- 不要把失败数据泄漏进普通地点群聊。
## 9. 联调检查清单
前端检查：
- 进入地点后 `locationVisitId` 稳定；离开再进刷新。
- 每个顾客开始调酒后拿到新的 `conversationId`。
- 自由聊天多轮后，顾客回复和头像/名字仍绑定当前这位顾客。
- 推荐回复显示在顾客回应后面。
- Day2 剧情引导不被后端推荐覆盖。
- 失败后可以重调，不会卡死在 submitted 状态。
后端检查：
- `/bartending/session` 写入独立 session marker。
- `/location-chat/messages` 带 `bartendingSessionId` 时只走调酒上下文。
- `/location-chat/history` 只拉当前 `conversationId`。
- 普通地点聊天排除调酒隐藏 marker。
- `/bartending/submit` 失败时允许 retry。
- 结算 review 由 LLM 生成后做必要清洗，但不要用强规则误杀常见中文表达。

## 11. 建议联调顺序
1. 后端单独启动，确认接口可用。
1. 选 2-3 个不同角色，各跑一轮通过和不过。
1. 每个角色至少聊 5-6 轮，观察顾客回复、推荐回复、配方评分。
1. 调酒后回普通地点群聊，检查是否出现 score / passed / threshold / 小费等调酒内部数据。
1. 离开地点再回来，检查同一 agent 是否刷新“今天喝过的酒”上下文。
1. 失败后立刻重调，确认不需要重新进入地点也能 retry。

## 12. `staging.zoooo.com` 手工验收步骤
### 12.1 准备
- 打开 `https://staging.zoooo.com`，使用可进入 Zoooo town 的测试账号登录。
- 部署后先强刷页面，再进入一个有 agent 的地点。
- DevTools Network 只用于确认请求边界；优先从 UI 体验判断是否符合预期。
### 12.2 普通地点群聊回归
操作：
1. 进入普通地点，不打开调酒。
1. 打开地点群聊。
1. 用玩家口吻发 2-3 条短消息。
预期：
- agent 回复自然贴合当前地点和话题。
- 群聊里不出现调酒评分、配方、threshold、passed/failed、小费、drink JSON 等内部数据。
- 推荐回复是可直接发送的短句 label。
### 12.3 调酒启动为独立会话
操作：
1. 从地点里打开调酒 / mix-drinks 入口。
1. 确认顾客先提出饮品需求。
1. 和顾客聊 5-6 轮，玩家发言参考自然玩家语气，优先点推荐回复再补少量自由输入。
预期：
- 每次进入调酒都从新的 conversation 开始。
- 顾客只围绕口味、心情、需求、玩家追问回应，不输出技术评分。
- 每次顾客回应后都有对应推荐回复 label。
- 推荐回复口吻像玩家，不像顾客或系统。
### 12.4 通过链路
操作：
1. 根据顾客需求选择 cup、base、mixers、garnish。
1. 提交一杯明显匹配需求的酒。
预期：
- 结果通过。
- 结算可以描述顾客对饮品的感受。
- 最后顾客 chat 不暴露 score、threshold、passed flag、小费金额或 raw recipe。
- 回到普通地点群聊后，仍不出现调酒内部数据。
### 12.5 不通过与 retry
操作：
1. 在同一次地点停留里再启动一位顾客。
1. 故意提交空配方或明显不匹配需求的酒。
1. 失败后直接 retry。
预期：
- 结果不通过。
- 顾客反馈仍保持角色口吻，不出现 fallback / system 式怪话。
- retry 可继续，不重复消费或重复惩罚同一次失败结果。
- 最后顾客 chat 仍不出现评分、小费、debug 信息。
### 12.6 同一次进入地点内避免重复喝酒
操作：
1. 不离开地点，连续服务同一个 agent 或同一批 agent。
1. 观察新一轮顾客需求。
预期：
- 新需求会参考这次进入地点期间已经喝过的酒。
- 在可避免时，不反复要求同一类饮品。
### 12.7 离开再回来刷新喝酒上下文
操作：
1. 离开当前地点。
1. 重新进入同一地点，再打开调酒。
预期：
- agent 的喝酒上下文随新的地点进入周期刷新。
- 旧调酒 transcript 不作为当前活跃 session 继续出现。
- 普通地点群聊历史仍只展示普通聊天，不混入调酒 score/debug 数据。
### 12.8 验收证据
每轮 staging 验收至少保留：
- 一条通过链路截图或录屏。
- 一条不通过链路截图或录屏。
- 调酒后回到普通地点群聊的截图，证明没有调酒内部数据泄漏。
- 如果失败，记录可见文案和所在步骤，不只贴 Network payload。
