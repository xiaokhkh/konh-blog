今天遇到一个很容易误判的网络问题：

同一个 Wi-Fi 下，一台电脑可以 ping 通自己的 VPS，另一台电脑却 ping 不通。第一反应很容易往 VPS 防火墙、运营商出口、代理软件、UDP 协议这些方向想。但这次真正的根因更小，也更隐蔽：本机路由表里残留了一条错误的 host route。

这篇是脱敏后的复盘。文中的公网 IP、Wi-Fi 名称、内网网关、节点名称都用占位符表示。

## 现象

目标机器上执行：

```bash
ping TARGET_VPS_IP
```

结果不是普通的丢包，而是出现：

```text
ping: sendto: Network is unreachable
100.0% packet loss
```

但同一个 Wi-Fi 下，另一台电脑可以 ping 通同一个 VPS。

这条信息很关键。它把问题范围从“VPS 是否可达”缩小成了“这台电脑为什么不知道该怎么把包发出去”。

## 第一性原理：ping 不走系统代理

这类问题最容易被 Clash、mihomo、HTTP 代理、SOCKS 代理带偏。

但 ICMP ping 不走 macOS 的系统 HTTP 代理，也不走终端里的 `HTTP_PROXY`、`HTTPS_PROXY` 环境变量。除非开了 TUN/VPN 层面的透明代理，否则 ping 的路径主要由系统路由表决定。

所以正确的第一步不是看代理配置，而是看路由：

```bash
route -n get TARGET_VPS_IP
```

## 关键证据

当时机器已经切到了新的 Wi-Fi，默认路由是当前网络的网关：

```text
default
gateway: CURRENT_GATEWAY
interface: en1
```

但查询目标 VPS 的路由时，结果却是：

```text
route to: TARGET_VPS_IP
gateway: OLD_GATEWAY
interface: en1
flags: <UP,GATEWAY,HOST,DONE,STATIC>
```

问题就在这里。

`default route` 已经指向当前 Wi-Fi 的网关，但 `TARGET_VPS_IP` 这个单独目标却被一条更具体的 host route 指向了旧网关。这个旧网关属于之前的网络，在当前 Wi-Fi 下不可达。

路由匹配规则会优先使用更具体的路由。也就是说，即使默认路由是对的，只要目标 IP 有一条单独的 host route，系统也会优先走那条 host route。

于是 ping 报：

```text
Network is unreachable
```

不是因为 VPS 不在线，也不是因为 ICMP 被拦，而是因为本机把包发向了一个当前网络里不存在的下一跳。

## 为什么另一台电脑能通？

因为另一台电脑没有这条错误的 host route。

这也是这类问题容易误判的地方：两台机器看起来连的是同一个 Wi-Fi，但本机路由表、VPN/TUN 状态、静态路由、代理软件残留状态都可能不同。

同一个 Wi-Fi 只能证明“网络出口整体可能没问题”，不能证明“每台设备的路由状态一致”。

## 修复

删除这条错误 host route：

```bash
sudo route -n delete -host TARGET_VPS_IP
```

然后重新检查：

```bash
route -n get TARGET_VPS_IP
ping -c 6 TARGET_VPS_IP
```

正常情况下，目标路由应该回到当前 Wi-Fi 的默认网关：

```text
gateway: CURRENT_GATEWAY
```

如果删除后又自动出现，说明还有某个进程或脚本在持续写这条静态路由。下一步就要查：

```bash
pgrep -afil "clash|mihomo|surge|tailscale|wireguard|openvpn|sing-box|vpn"
netstat -rn -f inet
```

## 这次排障的最短路径

遇到“同 Wi-Fi 下 A 能 ping，B 不能 ping”的问题，不要先重装代理，也不要先换 DNS。按这个顺序查：

```bash
ping -c 4 TARGET_VPS_IP
route -n get TARGET_VPS_IP
netstat -rn -f inet
traceroute -n TARGET_VPS_IP
```

判断逻辑：

1. `ping` 显示 `Network is unreachable`：优先看本机路由，不是先看远端防火墙。
2. `route -n get` 里有 `HOST` 或 `STATIC`：优先怀疑残留 host route。
3. 目标 IP 的 gateway 和 default gateway 不一致：问为什么这一个目标被特殊处理。
4. 同网另一台能通：远端 VPS 和 Wi-Fi 出口大概率不是主因。
5. `traceroute` 报 `Can't assign requested address`：通常也是本机路由或源地址选择出了问题。

## 代理软件在这里扮演什么角色？

这次机器上同时经历过 Clash 和 mihomo 切换，而且系统代理端口也被调整过。它们会影响浏览器、curl、开发工具访问 HTTP/HTTPS 资源，但不是这次 ping 失败的直接原因。

真正的问题是：目标 VPS IP 被写进了系统路由表，且下一跳还停留在旧网络。

代理软件、VPN、TUN、测试脚本都有可能间接制造类似残留路由，但排障时不能直接归因。必须以路由表为准。

## 复盘结论

这次问题的根因是：

**切换网络后，本机仍保留了一条指向旧网关的目标 VPS host route。系统优先匹配这条更具体的路由，导致 ping 和 TCP 连接都无法从当前 Wi-Fi 正确发出。**

真正改变判断的信息只有两条：

```text
default gateway: CURRENT_GATEWAY
TARGET_VPS_IP gateway: OLD_GATEWAY
```

看到这两条，问题就不该再往 VPS 防火墙、DNS、HTTP 代理上发散。

网络问题的第一性原理很简单：包要先知道从哪里出去。连这一步都错了，后面的代理、协议、节点质量都还没轮到。
