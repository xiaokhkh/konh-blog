SPZ 不是一种可以直接塞进 `<Model />` 的普通 3D 模型文件。它代表的是另一套渲染范式：3D Gaussian Splatting。

这篇记录的是我现在在 `react-native-filament` 上做 SPZ 支持时采用的架构拆法：底层让 React Native Filament 真正具备 native SPZ/Gaussian Splat 渲染能力；上层再用一个独立包承接碰撞生成、角色移动、FPS 漫游和场景工具。

最短的结论是：

```text
App / Demo / Product Scene
  -> react-native-filament-spz
  -> react-native-filament fork
  -> Filament native GPU backend
```

`react-native-filament` fork 只承载渲染底座。`react-native-filament-spz` 承接 SPZ 相关的上层产品能力。

## 为什么不是 SPZ 转 GLB

“SPZ 转 GLB”听起来像格式转换，但实际跨的是渲染范式。

`<Model />` 路径加载的是传统 glTF/GLB mesh：三角形、材质、贴图、UV、法线。SPZ 存的是 Gaussian Splats：位置、尺度、旋转、透明度、颜色或球谐信息。它没有天然的三角面，也没有 mesh renderer 能直接理解的表面拓扑。

所以这里有两个容易混淆的方向：

- 如果把 SPZ 重建成普通 mesh GLB，需要做网格重建、UV、法线和贴图烘焙。这是有损过程，复杂半透明、细碎结构、毛发感、树叶、反光都会退化。
- 如果把 splat 数据装进带 Gaussian Splatting 扩展的 GLB，runtime 仍然必须实现 splat 投影、排序、alpha blending 和着色。GLB 只是容器，不是渲染能力。

这也是为什么我没有把这件事理解成“喂给 `<Model />` 一个新文件格式”，而是把它当成一条新的 renderable 管线。

这四层的边界很重要：

| 层级 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| App / Demo | 场景组合、相机控制、交互、样例资产 | 不承载 SPZ 解码 |
| `react-native-filament-spz` | 碰撞生成、resolver、未来 FPS/角色 API | 不直接写 native renderer |
| `react-native-filament` fork | native SPZ renderer、TS API、material | 不绑定某个业务场景 |
| Filament | GPU 抽象、buffer、material、renderable | 不自动理解 SPZ 文件 |

这个边界决定了后续社区贡献的可接受程度。RNF 维护者更容易评审一个通用 renderer，而不是一个夹带私有场景、FPS 控制、碰撞生成、debug overlay 的大功能包。

```text
package/cpp/core/RNFSpzDecoder.cpp

```

`RNFSpzDecoder` 负责把 SPZ 文件里的 splat 数据读出来。`GaussianSplatResource` 负责把这些数据变成 Filament renderable。`EngineImpl.loadSpz` 是 JS/TS 调 native 的入口。`GaussianSplatWrapper` 把 native resource 暴露成 JS 可操作的对象。

## React Native API

React 侧有两个入口。

一个是 hook：

```tsx
const splat = useGaussianSplat(source, {
  addToScene: true,
  maxSplats,
  splatScale: 1,
  metricScaleFactor,
  groundPlaneOffset,
  flipY,
})
```

另一个是组件：

```tsx
<GaussianSplat source={require('./scene.spz')} />
```

`useGaussianSplat` 内部做几件事：

1. 通过 `useBuffer` 读取 `.spz`。
2. 读取默认 splat material。
3. 调 native `engine.loadSpz(...)`。
4. 拿到 native `GaussianSplatAsset`。
5. 把 entity 加进 Filament scene。
6. 返回 bounding box、root entity、point count 等信息。

所以在 React 侧，它应该像 RNF 里其他资源 hook 一样使用。真正复杂的 splat 解码、排序和 GPU buffer 构建都在 native 层。

## 资产策略

公开仓库里不应该带私有大场景。当前那份 `1-world-500k.spz` 和它派生出的 collision/debug/voxel 数据，都不适合直接推到社区 fork。

现在推上去的范围是：

- native SPZ/Gaussian Splat renderer；
- 默认 splat material；
- `useGaussianSplat` 和 `<GaussianSplat />`；
- `react-native-filament-spz` workspace 包；
- collision segment resolver；
- 通用 collision generation CLI。

没有推上去的是：

- 私有 SPZ 场景；
- 由它生成的 collision/debug/voxel 文件；
- 本地 FPS 漫游 demo；
- iOS UI 漫游测试；
- 本地角色球材质。

后续如果要做社区 demo，应该找一个小型、license-clean 的 SPZ 样例。这个样例只需要证明：RNF 能加载 SPZ、可以切换 debug、可以做最小相机控制。复杂 FPS 漫游可以放到独立示例或后续文章里。

## 社区贡献路线

我倾向于分四步推进。

### 1. 先稳定 RNF fork 的 SPZ renderer

第一步只聚焦 native SPZ decode、Gaussian splat renderable、`useGaussianSplat`、`<GaussianSplat />` 和类型。不要让 PR 夹带私有场景资产和 FPS 业务逻辑。

### 2. 把上层包做成 publish-ready

`react-native-filament-spz` 现在已经有包形态，但后续要去掉 `private: true`，整理 peer dependency、README、CLI 文档和最小测试。

### 3. 补一个 license-clean 小样例

替换当前本地大场景，提供小型 SPZ + 最小 demo。这个 demo 的目的不是秀效果，而是证明渲染链路和 API 形态。

### 4. 再推进 FPS/角色漫游

等 renderer 和上层包边界稳定后，再把 camera controller、角色碰撞、debug overlay 作为增量功能推进。

## 最核心的判断

这套架构的核心不是“支持一个新文件后缀”，而是把 SPZ 作为 React Native Filament 的一种新 renderable 处理。

底层回答的问题是：React Native Filament 能不能正确渲染 SPZ。

上层回答的问题是：SPZ 怎么变成可漫游、可碰撞、可产品化的场景。

这两个问题应该分开解决，也应该分开贡献。
