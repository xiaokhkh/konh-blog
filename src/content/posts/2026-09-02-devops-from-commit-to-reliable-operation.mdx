最近排查过一条看起来已经成功的发布链路：代码扫描通过，单元测试通过，镜像全部推送，数据库迁移完成，Pod 也都 Ready。

但客户端还是连不上。

继续沿真实请求检查，才发现 HTTP 健康检查正常，HTTPS 也能完成 TLS 握手，证书本身没有问题，可请求在握手之后被直接断开。Kubernetes Service 只声明了 HTTP 和两个 WebSocket 端口，云上的 443 Listener 则是在声明式配置之外单独维护的。证书还在，后面的 Target Group、协议或健康目标却已经和当前 Service 脱节。

流水线全绿，只能证明流水线检查过的那些事情成立。它没有证明用户真的能使用系统。

这类事故很适合用来重新理解 DevOps。DevOps 不是把 Jenkins 换成云效，不是会写 Dockerfile 和 Kubernetes YAML，也不是让开发拥有生产权限。它要解决的是一个更基础的问题：

> 怎样让一次代码变化，以可重复、可验证、可审计、可回滚的方式，变成线上真实可用的能力，并尽快把运行结果反馈给下一次决策？

## DevOps 是一条反馈闭环

传统交付经常被切成几个彼此断开的部门：产品提出需求，开发写代码，测试验收，运维部署，线上出事后再跨群找人。每个角色都完成了自己的局部任务，但没有人拥有从变化到结果的完整闭环。

DevOps 真正优化的是这条价值流：

```text
计划
 → 编码
 → 构建
 → 验证
 → 发布
 → 部署
 → 运行
 → 观测
 → 学习
 → 下一次计划
```

自动化只是缩短闭环的方法。更重要的是，每一阶段都有明确的输入、输出和证据：

| 阶段 | 输入 | 输出 | 必须回答的问题 |
| --- | --- | --- | --- |
| 编码 | 需求与约束 | 可评审的变更 | 为什么改、影响什么 |
| 构建 | 确定的源码版本 | 不可变制品 | 能否重复得到同一结果 |
| 验证 | 制品与测试环境 | 质量证据 | 哪些风险已经被验证 |
| 发布 | 已验证制品 | 可部署版本 | 准备发布的是哪一个版本 |
| 部署 | 版本与环境声明 | 运行中的系统 | 实际环境是否达到期望状态 |
| 观测 | 真实流量与运行数据 | 反馈与告警 | 用户是否真的获得预期结果 |

只自动化中间的 shell 命令，而没有建立这些契约，得到的通常只是一条跑得更快的脚本。

## 先分清六种不同的对象

很多混乱都来自把不同生命周期的对象放在一起管理。

### 源代码

源代码描述应用逻辑，应该能够被评审、测试、追踪和回退。一次提交只是候选变化，不是可以直接进入生产的发布物。

### 制品

制品是构建阶段的输出，例如容器镜像、二进制、APK、IPA 或静态网站。合格的制品应该是不可变的，并能通过版本号、哈希或镜像 digest 唯一定位。

```text
commit SHA → build → image digest
```

同一个版本在测试、预发和生产之间晋级时，应该移动同一份制品，而不是每个环境重新构建一次。重新构建意味着重新引入依赖漂移、构建环境变化和供应链风险。

### 部署配置

Deployment、Service、Ingress、Gateway、Helm Chart 和 Kustomize overlay 描述制品如何运行。它们属于期望状态，也必须版本化，但不一定要和业务代码放在同一个仓库。

### 环境配置

测试和生产的副本数、域名、资源配额、功能开关不同。这些差异应该被明确表达为变量或 overlay，而不是复制两套逐渐分叉的 YAML。

### 基础设施

集群、网络、负载均衡器、DNS、证书、IAM 和数据库属于环境基础设施。它们通常比单个应用生命周期更长，也由不同权限边界管理，更适合放在独立的 Terraform 等基础设施代码中。

### Secrets

密码、Token、私钥和云访问凭据既不是业务代码，也不是普通环境变量。它们需要专门的密钥系统、最小权限、轮换策略和访问审计。Base64 只是编码，不是加密。

## CI 的终点是可信制品

Continuous Integration 经常被误解成“代码提交后跑一下测试”。更准确的定义是：团队持续把小规模变更集成到主干，并为每次集成快速建立可信度。

一条完整的 CI 至少包含：

```text
检出确定提交
 → 锁定依赖
 → 静态检查
 → 单元与集成测试
 → 构建
 → 安全与依赖扫描
 → 生成 SBOM/元数据
 → 签名并推送制品仓库
```

它的终点不是“构建机上有一个目录”，而是制品仓库中存在一份可唯一定位、可下载、可验证来源的制品。

构建过程也应尽量可重复：固定工具链版本，使用 lockfile，不在步骤中临时修改源码，不依赖某台 Runner 的隐藏状态。缓存可以加速构建，但不能成为构建正确性的前提。

## CD 的起点是已经产生的制品

Continuous Delivery 负责让通过验证的制品随时处于可发布状态；Continuous Deployment 则进一步把满足规则的版本自动部署到目标环境。

无论采用哪一种，CD 都不应该重新承担 CI 的职责。部署阶段应当消费明确的制品版本：

```text
镜像 digest
+ 部署配置版本
+ 环境参数版本
= 一次可追踪的发布
```

这条等式同时定义了回滚需要什么。只记录“某次流水线成功”远远不够，必须知道当时到底运行了哪个镜像、哪一版编排和哪组环境参数。

测试环境可以自动部署，生产环境可以增加人工卡点、变更窗口、金丝雀或分批发布。但人工卡点应该审批明确的制品和风险证据，而不是让人凭感觉点击一个没有版本上下文的按钮。

云效 Flow 支持在 Job、Stage 和不同流水线之间传递制品，也支持从制品源选择已生成版本进行部署。这正是 CI/CD 分离和制品晋级的基础。[云效 YAML 流水线制品传递](https://help.aliyun.com/zh/yunxiao/user-guide/step-product-artifacts)

## Kubernetes YAML 到底放在哪里

答案取决于所有权和发布节奏，而不是某条绝对规则。

### 和应用放在同一个仓库

小团队、单服务、单一运行环境，可以直接使用：

```text
application/
├── src/
├── Dockerfile
└── manifests/
```

应用代码和部署结构由同一团队维护、一起评审、一起发布时，这种方式成本最低。云效官方 Kubernetes 示例也采用源码仓库同时保存 Dockerfile 和资源 YAML 的方式，并通过 Kubectl 发布步骤读取 YAML 路径。[云效 Kubernetes 部署概念](https://help.aliyun.com/zh/yunxiao/user-guide/analysis-of-key-concepts-of-pipeline) [使用云效构建镜像并部署到 K8s](https://help.aliyun.com/zh/yunxiao/use-cases/java-application-build-and-deploy-k8s)

问题不是 YAML 在业务仓库，而是仓库范围不断失控：应用清单旁边开始出现集群 RBAC、存储类、证书、DNS、数据库基础设施和多套环境副本。一次业务提交可能顺便改变整套平台。

### 使用独立配置仓库

当部署配置有独立所有者或需要跨环境晋级时，更清晰的结构是：

```text
application-repo
  业务代码、测试、Dockerfile

deployment-repo
  charts 或 base
  overlays/test
  overlays/staging
  overlays/prod

infrastructure-repo
  Terraform
  集群、网络、IAM、DNS、证书、Controller
```

云效 Flow 支持为一条流水线添加多个代码源，官方文档也明确列出从另一个 Git 仓库拉取 Kubernetes 配置文件的场景。[配置流水线源](https://help.aliyun.com/zh/yunxiao/user-guide/configure-pipeline-source)

过渡阶段可以让部署 Job 拉取配置仓库，渲染目标环境并执行 KubectlApply。进一步采用 GitOps 后，CI 只更新配置仓库里的镜像 digest，由 Argo CD 或 Flux 持续将集群校准到 Git 中的期望状态。

### 使用应用交付平台管理编排

不想自行维护 GitOps Controller 的团队，也可以使用云效 AppStack。AppStack 将 Kubernetes YAML 作为应用编排管理，为编排生成版本，并使用变量组渲染测试、预发和生产环境。Flow 产出镜像，AppStack 部署步骤组合制品、编排和环境执行发布。[AppStack 应用编排](https://help.aliyun.com/zh/yunxiao/user-guide/application-choreography/) [AppStack 与 Flow 的区别](https://help.aliyun.com/zh/yunxiao/user-guide/appstack-application-delivery-vs-flow-pipeline)

这三种方式不是官方定义的成熟度等级，也不是越复杂越先进。正确选择是：用能够清楚表达所有权、环境差异和回滚边界的最简单方案。

## 声明式配置为什么仍会失效

有了 YAML、有了 Ingress Controller 或 Load Balancer Controller，并不代表系统就不会漂移。

Controller 只能校准已经写进期望状态的内容。如果 Service 只声明 80，Controller 就只会维护 80。某个人在云控制台额外创建的 443 Listener，即使当天可用，也已经成为 Git 之外的隐藏状态。

一次完整的公网入口通常至少需要描述：

- DNS 与域名；
- 证书及其生命周期；
- 80/443 Listener；
- 后端协议和端口；
- HTTP、WebSocket 或 gRPC 路由；
- Target Group 健康检查；
- 超时、连接升级和安全策略。

Service、Ingress 和 Gateway API 只是不同抽象层。选择哪一个不如“整条链路是否被一个可审计的期望状态覆盖”重要。

## Secrets 和权限决定了系统的爆炸半径

最省事的流水线往往给构建机一组长期云密钥，再允许它对整个集群执行任意 `kubectl`。这也意味着一次依赖投毒、一段错误脚本或一个泄露的日志，可能直接获得生产环境权限。

更合理的边界是：

- 代码读取、制品写入、测试部署和生产部署使用不同身份；
- 使用服务连接或短期凭据，而不是把长期密钥写进脚本；
- 部署身份只访问指定集群和命名空间；
- 生产发布需要更严格的准入和审计；
- Secret 存在云密钥服务，通过 External Secrets 等机制注入；
- 日志默认不输出环境变量、证书内容和 kubeconfig。

云效 Flow 与 AppStack 使用服务连接管理外部代码库、制品库和集群授权，并允许限定授权范围。AppStack 还可以围绕应用、环境和角色进一步划分权限。[云效 AppStack 全局设置](https://help.aliyun.com/zh/yunxiao/user-guide/global-settings-1/)

## 部署完成不等于交付完成

Kubernetes 报告 Deployment Ready，只说明探针定义的条件成立。它不证明公网 DNS、TLS、网关路由、第三方依赖和客户端配置都正确。

验证应该分层：

```text
容器层    进程启动、端口监听
集群层    Service 可达、Readiness 正常
入口层    DNS、证书、HTTPS、WSS、路由正常
业务层    登录、鉴权、核心读写链路正常
用户层    真实客户端可以完成关键任务
```

如果系统对外提供 HTTPS 和 WebSocket，发布后的冒烟检查至少应该覆盖：

- HTTPS 健康接口返回预期状态；
- 证书域名匹配且未临近过期；
- WebSocket Upgrade 成功，或返回预期的鉴权错误；
- 每个关键路径被转发到正确后端；
- 工作负载运行的是本次发布的镜像 digest；
- 所有迁移和滚动更新完成；
- 错误率、延迟和饱和度没有越过阈值。

监控也不只是部署后的仪表盘。日志、指标、Trace、SLO 和业务事件要能回到具体发布版本，才能回答“这个异常是否由刚才的变化引起”。没有版本关联的观测数据，很难形成反馈闭环。

## 在云效中怎样落地一条完整链路

以一个部署到 Kubernetes 的后端为例，可以把云效能力映射为：

```text
Codeup
  管理业务代码与部署配置

Flow CI
  代码扫描 → 测试 → 构建 → 推送镜像 → 产生制品元数据

制品仓库
  保存不可变镜像或软件包，承接环境晋级

Flow CD / AppStack
  选择制品 → 选择环境 → 渲染编排 → 发布 → 验证

服务连接与变量组
  管理外部资源授权和环境差异

监控与告警
  把真实运行结果反馈给发布记录和负责人
```

一条务实的多仓库流水线可以写成：

```text
主分支提交
 → 并行静态检查与测试
 → 构建一次镜像
 → 推送并记录 digest
 → 拉取部署配置仓库
 → 更新测试环境 overlay
 → 部署测试环境
 → HTTPS/WSS/业务冒烟
 → 记录验证证据
 → 同一 digest 晋级预发
 → 人工或策略准入
 → 同一 digest 晋级生产
 → 金丝雀观察
 → 自动完成或回滚
```

流水线源是 Flow 的输入，制品是阶段之间的稳定契约，环境是部署目标，AppStack 则把应用编排、环境和发布版本组织在一起。把这些对象分清以后，流水线本身反而会变得简单。

## 常见的反模式

下面这些现象通常意味着交付系统开始失去边界：

- 在流水线命令里临时修改源码再构建；
- 测试、预发和生产分别重新构建镜像；
- 使用 `latest`，无法定位真实版本；
- Kubernetes YAML 一部分在 Git、一部分在流水线脚本、一部分靠控制台手工创建；
- 把 Base64 当成 Secret 管理；
- 构建 Runner 持有长期生产管理员密钥；
- 部署只检查 Pod Ready，不检查真实域名和业务路径；
- 遇到声明冲突就永久使用 `--force-conflicts`，却不先确定字段所有者；
- 所有环境共用一条无法审计差异的流水线；
- 回滚只是“重新跑上一次”，而不是恢复确定的制品和配置版本。

## 从能跑到可靠，可以分四步

不需要一次性引入所有平台和 Controller。更安全的演进顺序是：

1. 先让构建可重复，镜像不可变，并记录 commit 到 digest 的映射。
2. 再拆分 CI 与部署 Job，让测试、预发、生产晋级同一制品。
3. 将环境部署配置集中到 Git 或 AppStack，消除控制台手工状态，并建立最小权限。
4. 最后补齐外部冒烟、可观测性、渐进发布和自动回滚，形成真正的反馈闭环。

每一步都应该减少隐藏状态，而不是只增加新工具。

## 最后

DevOps 的核心不是开发和运维都学会对方的命令，而是共同拥有从变化到运行结果的系统。

代码必须能追踪到制品，制品必须能追踪到部署，部署必须能追踪到环境，环境必须能反馈真实用户结果。任何一个环节只存在于某台机器、某条临时命令或某次控制台点击里，闭环就会断掉。

所以评价一条 CI/CD 流水线，不要只问它有没有自动构建、自动部署。更应该问：

> 当线上结果和预期不一致时，我们能否快速知道运行的是什么、配置来自哪里、变化由谁引入、哪些证据曾经通过，以及如何安全回到上一个确定状态？

能稳定回答这些问题，才说明 DevOps 系统真正开始工作。
