The center of these documents is not "store more history." The center is: make past experience re-enter the model as high-quality, permission-aware, traceable context.

## Key takeaways

- Memory is only useful when it becomes future prompt context.
- The target architecture separates raw transcript, memory item, embedding thunk, graph edge, relationship state, and context composer.
- The Recall Planner should be a lightweight rule-based plan selector by default, not an LLM on the hot path.

## Source alignment

The target implementation document reframes the work away from "Recall Planner as the main character." The planner becomes one component in a larger recall chain.

The source docs distinguish:

- current architecture vs target architecture,
- raw memory vs intermediate recall data,
- rule-based recall planning vs LLM-based reasoning,
- text retrieval vs graph-constrained state,
- subjective relationship state vs factual evidence.

That is the important alignment: memory is a pipeline, not a single vector search call.

## The memory pipeline

A useful long-term memory stack has several layers:

- Raw transcript: the full source record for audit and re-extraction.
- Memory item: a subjective summary of a meaningful experience.
- Embedding thunk: a small semantic evidence unit that can be retrieved independently.
- Graph edge: structured state such as ownership, location, visibility, or relationship.
- Relationship state: accumulated attitude over time.
- Context composer: the final policy for what enters the prompt.

Each layer answers a different question. Collapsing them into one "memory" table makes recall noisy and hard to debug.

## Embedding thunks are evidence units

The Embedding Thunk document is specific: a thunk is not a random token chunk. It is the smallest semantic unit that can independently support a claim.

A single memory may contain:

- a location change,
- an object transfer,
- a witness,
- an emotional reaction,
- a future plan,
- an uncertainty boundary.

Those should not be embedded as one mixed paragraph. They should become separate thunks so retrieval can answer precise questions such as "Who has the map?" or "Why does Jam trust the user more?"

## Graph recall handles state and visibility

Text retrieval is good at semantic similarity. It is weaker at state questions:

- Who currently owns the object?
- Which fact is newer?
- Which character knows this?
- Did this relationship change expire?
- Which evidence supports the answer?

The graph layer helps constrain recall before the model answers. It does not replace text memory. It gives the system current state, visibility, and traceability.

## Recall Planner should stay lightweight

The Recall Planner document explicitly says the planner should not default to LLM reasoning. The main path should be a rule-based plan selector.

That keeps the hot path stable:

- choose recall strategy,
- select memory types,
- apply visibility rules,
- retrieve thunks and graph state,
- compose compact context,
- let the final model answer.

Use an LLM in the planner only when the rule path is insufficient.
